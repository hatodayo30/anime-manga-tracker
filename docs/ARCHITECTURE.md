# 実装まとめ（アーキテクチャと処理フロー）

このリポジトリで「何がどう動いているか」を一枚で掴むための文書。
セットアップ手順と API 一覧は `README.md`、残タスクと着手順は `BACKLOG.md` を見ること。

最終更新: 2026-10-04

---

## 概要

観ているアニメ・読んでいる漫画の進捗を記録し、今季の新作や人気作を探せる Web アプリ。
作品情報は AniList の GraphQL API から取得し、MyAnimeList 由来のランキングと掲載誌を
Jikan API で補完している。

Go (Echo) のシングルバイナリが API と React 製フロントエンドの静的ファイルを両方配信する。
DB は PostgreSQL 16 で、マイグレーションはバイナリに焼き込まれ起動時に自動適用される。
外部 API はいずれも API キー不要。

設計上の軸は 3 つ。

- **依存性逆転** — usecase 層がリポジトリ / ゲートウェイのインターフェースを自分で定義し、
  infrastructure と外部 API クライアントがそれを実装する。
- **プロセス内で完結** — キャッシュ・single-flight・レート制限のトークンバケット・定期ジョブは
  すべて 1 プロセスのメモリ上にあり、外部のミドルウェア（Redis 等）に依存しない。
- **外部 API のレートを守る** — AniList 30 req/分・Jikan 3 req/秒という上限が、
  キャッシュ設計からジョブ間隔まで多くの判断を規定している。

このプロセス内完結という前提は、**水平スケールを封印する**ことと引き換えに成立している。
2 タスク並走で実効レートが倍になり 429 を踏むため、デプロイ時も単一タスクを保証する必要がある。

## 技術スタックと構成

| レイヤ | 使用技術 |
| --- | --- |
| バックエンド | Go 1.25 / Echo v4 / pgx v5 |
| フロントエンド | React 19 / TypeScript / Vite / React Router v7 |

レイヤは handler → usecase → repository / gateway の 3 層で、向きは常に内側を向く。

```

│ ルーティング・認証ミドルウェア │  │ 8 分ごと  home-cache-warm      │
│ 静的ファイル配信（SPA）        │  │ 30 分ごと next-airing-sync     │
└───────────────┬───────────────┘  └───────────────┬───────────────┘
                v                                  v
┌─ internal/usecase ────────────────────────────────────────────────┐
│  record   auth   search   home   translate   airing               │
│  cache.TTLCache — single-flight / stale-while-revalidate          │
└───────────────────────────────┬───────────────────────────────────┘
                                v 呼ぶ
╔═ Repository / Gateway インターフェース（usecase が定義） ══════════╗
╚═══════════════╤═══════════════════════════════╤═══════════════════╝
                ^ 実装する                      ^ 実装する
┌─ infrastructure/postgres ─────┐  ┌─ anilist / jikan / translate ─┐
│ pgx v5 / 起動時マイグレーション │  │ レート制限つきクライアント      │
└───────────────┬───────────────┘  └───────────────┬───────────────┘
                v                                  v
         PostgreSQL 16                 AniList / Jikan / MyMemory
```

入口は HTTP リクエストと定期ジョブの 2 つで、どちらも同じ usecase を通る。

## データモデル

テーブルは 4 つだけ。中心は `records` で、1 行が「ある利用者の、ある作品 1 作品分の記録」を表す。
AniList の作品情報（タイトル・表紙・ジャンル）を正規化せず行に貼り付けているので、
作品マスタテーブルは存在しない。

| テーブル | 役割 | 主な制約 |
| --- | --- | --- |
| `users` | メール + bcrypt ハッシュ | `email` は UNIQUE |
| `sessions` | セッショントークンと有効期限 | `token` が PK、`user_id` は ON DELETE CASCADE |
| `records` | ライブラリの 1 作品 | `(user_id, anilist_id, media_type)` が UNIQUE。`media_type` と `status` は CHECK 制約 |
| `applied_migrations` | 適用済みマイグレーションの記録 | ランナーが管理 |

`records` のカラムで挙動が自明でないもの。

| カラム | 意味 |
| --- | --- |
| `progress` / `total` | 単位は `media_type` で決まる——アニメは話数、漫画は巻数。専用カラムを増やさない設計 |
| `next_airing_at` | 次話放送日時。追加時はクライアントから渡され、以後は `next-airing-sync` ジョブが書き戻す |
| `rating` | 1〜5 の CHECK 制約。API で 0 を渡すと NULL（未評価）に戻る |
| `genres` | `TEXT[]`。おすすめ画面のジャンル集計に使う |
| `updated_at` | 利用者の操作でだけ更新される。定期ジョブは意図的に触らない |

マイグレーションは現在 4 本。`0001` が `records`、`0002` がユーザー・セッション追加と
`records` のユーザースコープ化、`0003` が評価とメモ、`0004` が漫画の進捗を話数から巻数へ
切り替えるデータ移行。

`0004` はカラムを追加せず、漫画レコードの `progress` を 0、`total` を NULL に戻すだけにしている。
話数は巻数に換算できないためで、`total` は作品モーダルが AniList の最新情報を取得した
タイミングで PATCH で同期される。

## 主要機能と処理フロー

画面は 6 つ。ホーム・シーズン・おすすめはログイン不要で、検索とマイライブラリは
`ProtectedRoute` で囲っている。アニメ / 漫画の切り替えは `useKind` が localStorage で
全画面に共有する。

| 画面 | 叩く API | 処理の要点 |
| --- | --- | --- |
| ホーム `/` | `/api/home/season-anime`・`/api/home/trending-manga`・`/api/records` | 今週放送の人気アニメ TOP10、曜日別スケジュール、話題の漫画 TOP10。ランキングは `useRef` でタブ往復の再取得を避ける |
| シーズン `/season` | `/api/home/season-anime?season=&year=` | サーバーが 40 件まとめて返し、20 件 × 2 ページをクライアントで切り出す。ページ送りで追加の API 呼び出しは起きない |
| 検索 `/search` | `/api/search?type=&q=` | AniList 検索。ヒットが 3 件以下なら Jikan でも検索し、タイトル重複を除いて人気順にマージ |
| マイライブラリ `/library` | `/api/records?type=&sort=` | 種別と並び順だけをサーバーに渡し、ステータス絞り込み・ジャンル絞り込み・集計は取得済み配列を `useMemo` で加工 |
| おすすめ `/recommend` | `/api/recommendations?type=&genres=` | 「どのジャンルを見るか」はクライアントがライブラリを集計して決めるので、API 自体はログイン不要 |
| ログイン / 登録 | `/api/auth/*` | `AuthContext` が起動時に `/api/auth/me` を叩いてログイン状態を解決 |

### 作品モーダル

全画面から開く共通のモーダルで、作品ごとに `key` で再マウントされる。
マウント時に 3 本の取得を並行で走らせる。

1. `/api/anilist/media` — 総話数・放送状況の最新化
2. `/api/anilist/relations` — 関連作品（続編・前日譚・スピンオフ）
3. `/api/translate` — あらすじを日本語へ機械翻訳

取得した `total` が保存済みの値とズレていれば、その場で PATCH して DB を同期する。
ライブラリ画面の進捗バーと「全巻読了で done へ」の判定は DB の値だけを見るためで、
漫画の話数→巻数移行（マイグレーション `0004`）の残りもここで埋まる。

進捗を `total` まで進めるとステータスを自動で `done` にする。未ログインでステータスを押すと
`/login?next=` 付きでログイン画面へ逃がす。

### リクエストが通る道筋

ルーターは `/healthz` → `/api/records/*`（`RequireUser` 付き）→ その他の `/api/*` → `/*`
の順で登録され、最後のワイルドカードが `frontend/dist` へフォールバックする（SPA ルーティング）。
`/healthz` を先に登録するのは、ワイルドカードに食われないようにするため。

ヘルスチェックは DB の `Ping` までに留め、AniList / Jikan は叩かない——チェックのたびに
上流のレート制限を消費してしまうため。タイムアウトは 2 秒で、ECS のコンテナヘルスチェックの
既定 5 秒より短くして自分から 503 を返せるようにしてある。

## 外部 API 連携

| API | 用途 | レート制御の方式 |
| --- | --- | --- |
| AniList (GraphQL) | 検索・シーズン一覧・人気ランキング・関連作品・ID 一括取得 | トークンバケット（2.5 秒に 1 個回復、バースト 5） |
| Jikan (MyAnimeList) | MAL ランキング・会員数・掲載誌、検索のフォールバック | 全呼び出しで最小リクエスト間隔 350ms を共有 |
| MyMemory | あらすじの日本語訳 | 1 リクエスト 450 バイト以下に文単位で分割 |

### AniList のトークンバケット

固定間隔ではなくトークンバケットを選んでいる。AniList の制限は「直近 1 分あたりの本数」という
窓で数えられており、一定間隔を強制されているわけではないから。これで画面の初期表示のように
短時間に数本重なるケースを待たせずに通せる。

実装は「バケットを使い切る時刻」（`allowAt`）を全呼び出しで共有する形。送信枠を先に予約するので、
並行する呼び出しどうしも間隔を守る。最悪ケースでも 5 + 60/2.5 = 29 本/分 に収まり、
目安の 30 req/分を超えない。

429 を受けたら `Retry-After` を読んで最大 3 回リトライするが、その際 `penalize` で
**共有バケットの再開時刻ごと後ろ倒しにする**。リトライ中の goroutine だけでなく、
同時に走る他の呼び出しもまとめて待たせるため。

### 外部障害を画面に漏らさない

補完的な情報の失敗は本体を止めない、という方針が各所に入っている。

- 話題の漫画の Jikan エンリッチは 1 件 4 秒のタイムアウト付きで並列実行し、
  失敗した作品は補足情報だけが空になる
- 検索の Jikan フォールバックが失敗しても AniList の結果はそのまま返す
- モーダルの 3 本の取得はどれも `.catch(() => {})` で、得られなかった要素が出ないだけ

Jikan 検索の結果は `anilist.SearchResult` の形に変換して返す。AniList に存在しない MAL 専用作品でも
一意に扱えるよう、`AniListID` には MAL ID の符号を反転させた**負の ID** を割り当てている。

## キャッシュ戦略

`internal/usecase/cache` の `TTLCache[T]` が 1 つだけあり、usecase が用途ごとに
インスタンスを持つ。プロセス内の `map` と `sync.Mutex` だけでできている。

| 用途 | TTL | stale 上限 | キー | 保持件数 |
| --- | --- | --- | --- | --- |
| ホーム（今季アニメ / 人気アニメ / 話題の漫画） | 10 分 | 100 分 | 固定（空文字） | 上限なし |
| シーズンブラウジング | 30 分 | 5 時間 | `season:year` | 64 件 |
| おすすめ | 3 分 | 30 分 | `type\|genres` | 上限なし |

シーズンブラウジングだけが件数上限付きなのは、`year` がクエリパラメータ由来で任意の数値を
取りうるから。上限を超えたら stale 切れ→古い順に捨てる。

### Get の分岐

```
Get(key)
  │
  ├─ 取得中？          ──はい──> 完了を待って結果を共有（single-flight）
  │
  ├─ age < TTL        ──はい──> そのまま返す
  │
  ├─ age < TTL×10     ──はい──> 古い値を返しつつ、裏で取り直す
  │                              （更新は 1 キー 1 本。失敗しても古い値は捨てない）
  │
  └─ いいえ           ────────> fetch の完了まで待たせる
                                 （値がまだ無いキーもここを通る）
```

待たされるのは一番下の経路だけ。`Refresh` はこの分岐を通らず、値を持っているキーを
待たせずに取り直す（ウォームアップ専用の入口）。

### 設計上決めたこと

- **古い値を返してよい上限は TTL の 10 倍**（`staleFactor`）。超えたら待たせてでも取り直す
- **バックグラウンド更新は 1 キーにつき常に 1 本**。stale な値への同時アクセスが重なっても
  上流に更新が積み上がらない
- **更新が失敗しても古い値は捨てない**。上流が一時的に落ちている間は stale 上限まで手元の値で凌ぐ
- **`Get` は `fetch` を引数で受け取る**。ハンドラの ctx はレスポンスを返した時点でキャンセルされるため、
  クロージャに閉じ込めたまま裏で使うと更新が必ず失敗する。バックグラウンド更新には
  `context.WithoutCancel` でキャンセルを外し、1 分の上限を掛けた ctx を渡す

エントリは不変で、バックグラウンド更新も既存エントリを書き換えず新しいエントリに差し替える。
待たせる側の fetch が先に結果を入れていた場合は、古い結果で上書きしない。

## 定期ジョブ

`internal/scheduler` は `Job{Name, Interval, Run}` を登録するだけのミニマルなランナーで、
起動直後に 1 回、その後は `Interval` ごとに実行する。現在 2 つのジョブが乗っている。

| ジョブ | 間隔 | すること |
| --- | --- | --- |
| `home-cache-warm` | 8 分 | ホーム向けキャッシュ 3 つを `Refresh` で取り直す |
| `next-airing-sync` | 30 分 | `next_airing_at` が過去になったアニメを AniList から引き直して書き戻す |

### ランナーの挙動

1 ジョブ 1 goroutine で**直列**に回す。前回が `Interval` を超えて長引いても、その間の tick は
捨てられるので、レート制限付きの外部 API を叩くジョブが二重に走ることはない。
ジョブが失敗しても止めず次の実行に進む（一時障害で二度と走らなくなるのを防ぐ）。
`Interval` が 0 以下のジョブはログを出して登録しない。

`Start(ctx)` が返す待機関数を `main.go` の終了処理で呼び、実行中のジョブが終わってから
DB プールを閉じる。

### ウォームアップ

温めるのはホーム画面の 3 つだけ。シーズンブラウジング用はキーが際限なく増えうるうえ
ホーム表示に使われないので対象外。間隔の 8 分はホーム向け TTL（10 分）より短くして、
TTL 切れを利用者が踏む前に裏で入れ替わっているようにしてある。
AniList は共通スロットルなので 3 つは直列実行。

実測で起動時のウォームアップが **6.2 秒**、温めたあとの `/api/home/*` は 3 本とも **1ms 台**。
この 6.2 秒が従来利用者の踏んでいた待ち時間。

### next_airing_at の同期

対象を「`next_airing_at` が過去のレコード」だけに絞っている。放送が 1 話進むと保存済みの値が
過去になる、というのが腐り方そのものだから。引き直した結果は未来の日時か NULL のどちらかになり、
いずれも次回以降は対象から外れる。**処理すべき件数が 0 に収束する**ので、定常状態での
AniList 消費はほぼゼロ。

その他の判断。

- **1 回あたり最大 100 ID**。`MediaByIDs` が 50 件を 1 リクエストにまとめるので AniList 最大 2 リクエスト
- **問い合わせたのに AniList が返さなかった ID には NULL を書く**。放置すると過去の日時が残って
  毎回の対象に居座り、枠を食い潰して収束しなくなる
- **`updated_at` は触らない**。裏での同期であって利用者の操作ではないので、更新すると
  「最近更新した順」が定期ジョブで塗り替わる。同じ理由で、値が変わらない行は
  `IS DISTINCT FROM` で弾く
- **同じ作品を複数の利用者が登録していても問い合わせは 1 回**。書き戻しも配列を渡す 1 文の UPDATE にまとめる
- **AniList が失敗したら何も書かない**。取れなかったぶんを NULL で潰すと、一時障害で
  全ライブラリの次話表示が消える

実測（ローカル DB、腐ったレコード 31 件）では、起動時の 1 回で全件が解消し **476ms**。
`updated_at` は 1 行も動かなかった。

残っている穴は、**`next_airing_at` が最初から NULL のレコードが対象外**なこと。
放送終了作品ではこれが正しいが、「放送予定がまだ決まっていない時期に追加した未放送アニメ」は
NULL のまま固定される。拾うには巡回カーソル用のカラム追加が要る。

## 認証と境界

メール + パスワードの自前実装。パスワードは bcrypt（`DefaultCost`）でハッシュし、
セッショントークンは `crypto/rand` の 32 バイトを base64url でエンコードしたもの。
有効期限は 30 日で、HttpOnly Cookie で配る。

`Secure` 属性は `COOKIE_SECURE`（既定 `false`）で切り替える。真偽値として読めない値は
既定値に倒さず**起動時エラー**にする——`ture` のような綴り間違いで `Secure` が黙って外れると
気付けないため。

### データの境界

ユーザースコープは**リポジトリの SQL で強制**している。`List` / `Update` / `Delete` はすべて
`WHERE ... AND user_id = $N` を含み、他人のレコードは `ErrNotFound` になる。
存在しないのか他人のものなのかを区別しない。

例外は `airing.Repository` だけで、こちらは定期ジョブが保守のために全ユーザーのレコードを
横断する。**インターフェースを分ける**ことで、ユーザースコープされない操作がそれと分かるように
してある（`RecordRepository` が両方を実装）。

### その他の安全側の扱い

- `ORDER BY` 句は SQL に直接埋め込むため、`domain.SortKey` → 句の
  **map に定義済みのものだけ**を使い、未知のキーは既定へフォールバックする
- ログイン失敗はメール未登録でもパスワード不一致でも同じ `ErrInvalidCredentials`
- `/healthz` は未認証で叩けるので、失敗の詳細はログにだけ残しレスポンスには出さない
- マイグレーションは `pg_advisory_lock` を掛けてから走る。単一タスク前提なら本来不要だが、
  設定ミスや手元からの直接実行と重なったときの保険

## テストと開発フロー

`go test ./...` は現時点で全パス。テストがあるのは 11 パッケージで、usecase 層が中心。
外部 API はインターフェース経由なので、usecase のテストはフェイクを差し込んでネットワークなしで回る。

最も厚いのは `internal/usecase/cache`（509 行）で、single-flight・stale-while-revalidate・
エビクションの振る舞いを押さえている。

### 穴

- **CI が `go test` を回していない**。gofmt / vet / build と、フロントの oxlint / tsc / vite build のみ
- **DB 依存の SQL に回帰テストがない**。`StaleAiringAnimeIDs` / `UpdateNextAiringAt` は
  使い捨てスキーマとローカル実行で手元確認しただけ
- **フロントエンドにテストがない**。型チェックと lint まで

### ローカル実行

全部 Docker で動かすなら `docker compose up --build` で `:8090`。ホットリロードするなら
DB だけ Compose で起動し、`go run ./cmd/server`（`:8090`）と `npm run dev`（`:5174`、`/api` はプロキシ）を
手元で回す。

Vite のプロキシ先ポートは `BACKEND_PORT` → `PORT` → `8080` の順で解決されるので、
`.env` の `PORT` を変えるなら Vite 側にも同じ値を渡すこと。

### マイグレーションの扱い

`golang-migrate` は**入れていない**。あちらの DB ドライバは `database/sql` 前提で、
既存の `pgxpool` とは別に接続を張ることになるため。乗り換え余地を残すため、記録テーブル名は
`schema_migrations` ではなく `applied_migrations` にしてある。

追加は `NNNN_name.up.sql` / `.down.sql` を連番で置くだけ。ロールバックは自動では行わず、
`.down.sql` を psql で流してから `applied_migrations` の該当行を削除する。

### デプロイで決まっていること

ECS Fargate を使う。これは**学習が目的**の選択であって、このアプリの要件から導かれたものではない
（Lightsail のほうが安く、ticker も素直に動き、`docker-compose.yml` がそのまま載る）。
コストの主因は Fargate 本体ではなく周辺リソースなので、NAT Gateway は作らず、
ALB は Phase 2 まで入れない。

必ず設定することが 1 つある——デプロイ戦略を `minimumHealthyPercent: 0` /
`maximumPercent: 100` にする。既定（100 / 200）だとローリングデプロイ中に 2 タスクが並走し、
AniList のレートを二重に消費する。

Spot 中断と再デプロイのたびにプロセス内キャッシュが空になるので、Fargate を選んだことで
stale-while-revalidate とウォームアップの価値はむしろ上がった。

### 知っておくべき制約

- **水平スケールできない**。キャッシュ・single-flight・トークンバケット・スケジューラが
  全部プロセス内。ElastiCache 等に出すまで解禁しない
- **表示言語をサーバーが決め打ちしている**。日本作品は native 優先、韓国・中国作品は
  english 優先のフォールバックが固定
- **あらすじの翻訳は毎回オンデマンド**。モーダルを開くたびに MyMemory を叩いており、
  キャッシュも永続化もしていない
- **セッションの期限切れ行が残る**。`sessions` を掃除するジョブはない
  （スケジューラ基盤はあるので、乗せるのは容易）
